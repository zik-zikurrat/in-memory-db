Tier 1 — конкретная польза, умеренная сложность
(DONE)
TTL / expiry для ключей
SET key value EX 30 — ключ живёт 30 секунд, потом удаляется. Научит: min-heap или time.AfterFunc, background goroutine для eviction, атомарность при concurrent доступе. Очень практично — используется везде (кэши, сессии, rate-limiting).

(DONE)
Sharded map вместо одного sync.RWMutex
Разбиваешь map[string]string на N сегментов (например, 16), каждый со своим mutex. Lock contention падает в N раз. Научит: hash-based partitioning, striped locking — один из самых важных паттернов для высоконагруженного Go-кода.
Запуск тестов
```
    go test -bench=BenchmarkMixed_ByWritePct -benchmem -count=10 -cpu=10 ./internal/database/storage/in_memory > res.txt
    benchstat res.txt
```


Snapshot (checkpoint) + усечение WAL
Сейчас при рестарте реплеится весь WAL с нуля — при больших данных это медленно. Добавить периодический снапшот всего состояния (encoding/gob или JSON), а после него WAL обнулять. Научит: сериализация, атомарная запись файлов (write → fsync → rename), coordination с WAL worker'ом.
Теперь картина ясна. Разберу, что сейчас не так, и как это делают правильно (по образцу Redis RDB).

Проблемы в текущем state_snapshot.go

1. Не компилируется. select заканчивается пустым case без выражения и тела, default нет — синтаксическая ошибка.
2. Snapshot не смотрит на реальные данные. state inmemory.Data создаётся как inmemory.Data{} — пустая структура, никак не связанная с engine, который реально пишет ключи. Даже если её проинициализировать через NewData(), Fork всё равно ничего в неё не пишет — некому.
3. Жёсткая привязка к одной реализации, причём нерабочая. Snapshot.state типизирован как inmemory.Data — это внутренности HashBasedPartitionMapEngine. Но Data.buckets и Partition.m — приватные поля, а state_snapshot.go лежит в пакете snapshots. Снаружи пакета inmemory прочитать их физически нельзя — код не соберётся, как только вы попытаетесь реально проитерироваться по данным. Плюс это ломает абстракцию: WAL и Storage работают через интерфейс storage.Engine (Set/Get/Del), а снапшот обходит его и лезет в конкретный движок — с SingleMapEngine/SyncMapEngine он вообще не заработает.
4. У storage.Engine нет способа перечислить все ключи. Это главная дыра: Set/Get/Del достаточно для WAL (он проигрывает лог команд), но снапшоту нужно снять слепок всего состояния — а обойти map он не может в принципе, интерфейс не даёт такой возможности.
5. Правила save (аналог save 900 1 / save 300 10 в Redis) не реализованы. Смысл: "если прошло ≥N секунд и накопилось ≥M изменений — сохранить". Сейчас есть только счётчик cnagesCnt, который растёт на каждое событие, но никто не проверяет его против s.save[duration], нет времени последнего сохранения на каждое правило, и нет тикера, который бы это периодически проверял (не нужно N таймеров под N правил — Redis делает это одним общим cron-тиком раз в секунду).
6. Нет самой записи снапшота на диск — ни сериализации (gob/JSON), ни atomic write (tmp-файл → fsync → rename), ни усечения WAL после успешного снапшота. WAL сейчас вообще не умеет обрезаться — такого метода нет.
7. Мелочи: опечатка cnagesCnt, Snapshot нигде не вызывается из main.go (не подключён).

Как сделать правильно

- Добавить в контракт возможность дампа состояния — либо расширить storage.Engine, либо завести отдельный интерфейс snapshots.Dumper:
type Snapshotable interface {
    Dump() map[string]string          // или ForEach(func(k, v string)) для стрима без двойной памяти
    Load(data map[string]string)      // восстановление при старте
}
- Реализовать в каждом engine с корректным блокированием (для HashBasedPartitionMapEngine — пройтись по всем Partition, взяв RLock на каждый).
- Snapshot должен держать не копию данных, а ссылку на движок/сторадж (Snapshotable) плюс lastSave time.Time и atomic-счётчик изменений.
- Fork — один time.Ticker (например, раз в секунду), на каждый тик проверяет все правила: changesSinceLastSave >= rule.Changes && time.Since(lastSave) >= rule.Duration → сохранить. Канал change только инкрементит счётчик (атомарно, т.к. пишут из воркера конкурентно).
- Сохранение — write tmp → fsync → rename (rename atomarен на одной ФС), затем сброс счётчика и, если нужно — уведомление WAL на усечение (это тоже отдельная фича, которую придётся добавить в wal.go).
- При старте (main.go) — сначала грузить снапшот, потом доигрывать WAL поверх него.

Tier 2 — структуры данных

LRU eviction при memory limit
Когда ключей больше N — выбрасывать наименее недавно использованные. Классика: doubly-linked list + hashmap. Это одна из самых часто задаваемых задач на собеседованиях, но реализация в реальном concurrent коде гораздо интереснее, чем на leetcode.

Cursor-based SCAN
SCAN cursor COUNT 100 MATCH user:* — итерация по ключам без блокировки всей БД. Учит lazy iteration, snapshot-at-cursor design, работу с glob-паттернами.

INCR / DECR
Простые атомарные операции над числовыми значениями. Небольшая доработка, но учит как делать read-modify-write атомарно без явного мьютекса в слое команд.

Tier 3 — архитектура и протоколы

RESP протокол
Redis Serialization Protocol — несложный бинарный протокол. Если реализуешь его, к твоей БД можно подключиться redis-cli и любой Redis-клиент. Учит: чтение спеки и её имплементация, wire protocol, binary parsing.

Pub/Sub
SUBSCRIBE channel / PUBLISH channel message. Учит: fan-out через каналы, управление подписчиками, broadcast без shared state.

Репликация (Leader → Follower)
Одна нода слушает WAL stream от другой и реплеит. Учит distributed systems fundamentals вживую — это уже серьёзно.
